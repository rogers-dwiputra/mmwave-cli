## 1. Eksplorasi Perangkat DSP (TDA / MMWCAS-DSP-EVM)

### 1.1 Identitas hardware & OS

| Item | Nilai |
|------|-------|
| Machine model (dmesg) | **TI DRA742 Cascade Radar Board** (SoC TDA2x / Jacinto) |
| Hostname | `dra7xx-evm` |
| CPU | 2× **ARM Cortex-A15** (ARMv7l 32-bit), NEON, terkunci **1.0 GHz** |
| RAM | 2622 MB, **tanpa swap** |
| OS | **Arago Linux 2016.12** (Yocto, distro TI untuk Sitara/DRA7xx) |
| Kernel | `4.4.84 SMP PREEMPT` (Aug 2019) |
| Init | systemd |
| SSH server | **Dropbear v2016.72** (bukan OpenSSH) + telnetd (port 23) aktif |

Selain A15, SoC TDA2 punya core C66x DSP, EVE, dan IPU (dipakai Vision SDK untuk
pipeline capture LVDS/CSI-2), tapi tidak diekspos sebagai remoteproc yang mudah dipakai
user.

### 1.2 Storage

| Mount | Device | Ukuran | Pakai | Catatan |
|-------|--------|--------|-------|---------|
| `/` (rootfs) | `/dev/root` | 1.5 GB | **72%** | kecil — rawan penuh (lihat §1.5) |
| `/mnt/ssd` | **`/dev/nvme0n1p1`** | 458 GB | **71%** (sisa 125 GB) | **NVMe**, tempat data capture |

Penting: SSD adalah **NVMe** (cepat secara lokal) — jadi I/O disk **bukan** bottleneck
transfer; bottleneck ada di jaringan (§3). SATA link down (tidak dipakai).

### 1.3 Cara DSP menerima & memproses perintah (arsitektur)

```
RPi (mimo.py → mmwcas.so) ──TCP 5001──► apps.out (TI Vision SDK) ──SPI──► 4× AWR2243
                                              │
                                              └─CSI-2/LVDS capture──► NVMe /mnt/ssd/<dir>
```

- Server capture = **`apps.out`** (PID 825), cwd `/opt/vision_sdk/`, **listen di port 5000 & 5001**.
- Dijalankan otomatis oleh **`vsdk.service`** (systemd, `Restart=always`) →
  `/opt/vision_sdk/autorun_cascade.sh`:
  - load modul `rpmsg_proto.ko`, set governor **performance**, mount NVMe ke `/mnt/ssd`,
    `vision_sdk_load.sh`, lalu `./apps.out`.
- `mmwcas.mmw_init()` membuka koneksi ke TDA (`MMWL_TDAInit` → port 5001), lalu mengirim
  rangkaian perintah **mmwavelink** (power-up, firmware download, channel/profile/chirp/
  frame config) yang diteruskan `apps.out` ke chip AWR2243 via SPI.
- Capture sebenarnya = `apps.out` menangkap stream CSI-2 dari RF-EVM dan menulis
  `master/slave1..3_0000_data.bin` + `_idx.bin` ke NVMe.

### 1.4 Beban CPU & termal (relevan untuk daya)

- **`apps.out` busy-wait**: TIME CPU 1h30 pada uptime 1h29 → praktis **memenuhi kedua core
  A15 100% terus-menerus** (load average konstan **2.00**), governor `performance`,
  hanya 1 frekuensi tersedia (1 GHz, tanpa DVFS). 64 thread.
- **Thermal zone 0–4: 80.6–84.2 °C** — SoC panas terus walau idle/tidak capture.
- **`systemd-journald`** ikut sibuk (~45%) karena membanjiri log (lihat §1.5).
- **Weston (Wayland GUI) + PowerVR GPU** jalan (`weston --idle-time=0`,
  `weston-desktop-shell`, `pvr_timer`, `pvr_workqueue`) — **sia-sia untuk operasi headless**,
  menambah daya & panas.

### 1.5 Risiko housekeeping yang ditemukan

- **`/opt/vision_sdk` 552 MB, 666 file `Trace_TDA_*.txt`** menumpuk di **rootfs yang hanya
  1.5 GB (72% penuh)**. Jika terus tumbuh → rootfs penuh → `apps.out`/boot bisa gagal.
  (read-only diamati; **belum dibersihkan** sesuai permintaan).
- `/run/log/journal` 122 MB (di RAM/tmpfs, aman tapi indikasi log berlebih).
- Banyak direktori capture lama di `/mnt/ssd` (mis. `Vital*_260612`, `Dimas`, `Tika`)
  tidak terhapus — auto-clean pipeline hanya menghapus dir berprefix `--label`.
- **eth1 tersedia tapi DOWN** (MAC `...6d:81`); `can0` ada (tak dipakai).

## 2. Peluang Hemat Daya (saat ini 12–16 W)

Konsumsi terbagi: **RF-EVM (4× AWR2243) ~12–14 W** (dominan) + **DSP board (TDA2) beberapa W**
(A15 100% + GPU/Weston + NVMe). Pada cadence 15 menit dengan capture 10 detik, **>99% waktu
adalah idle** namun seluruh sistem tetap menyala penuh.

### 2.1 Temuan yang langsung relevan

1. **Radar tidak pernah di-power-off antar capture.** API **ada** di source TI
   (`MMWL_powerOff()` → `rlDevicePowerOff()`, juga `rlSetPowerSaveModeConfig`,
   `rlRfDynamicPowerSave`) **tetapi TIDAK diekspos di `mmwcas.pyx`** (tidak ada di daftar
   `cdef extern`). Karena tiap siklus `pipeline.py` menjalankan `mimo.py` baru lalu keluar
   **tanpa power-down**, chip AWR2243 tetap powered/configured selama belasan menit idle.
2. **TDA2 di-pin di 1 GHz governor `performance` + apps.out busy-wait** → daya & panas
   konstan walau tidak ada capture.
3. **TDA2 mendukung suspend-to-RAM**: `/sys/power/state` = `freeze mem`.

### 2.1b Klarifikasi penting: `powerOff` software ≠ power-off hardware (NRESET)

> Menjawab pengalaman user: "`powerOff` pernah dipanggil tapi tak ada respon."

- **Power-off AWR2243 yang sesungguhnya = pin hardware `NRESET`.** DFP User Guide menyatakan:
  *"NRESET: Output from external processor to reset AWR2243 device. To power up AWR2243,
  NRESET = 1. To power Off, NRESET = 0."* Pin `NRESET` (dan `SOP`) dikendalikan **TDA2/`apps.out`**,
  bukan oleh mmwavelink dari sisi RPi.
- `MMWL_powerOff()` → `rlDevicePowerOff()` hanyalah **de-inisialisasi software link mmwavelink**
  (menutup komunikasi SPI-over-Ethernet, membongkar state driver). Akibatnya:
  - Bukan perintah penghasil data → **tidak ada ACK/output** ("tak ada respon" itu normal).
  - **Tidak menurunkan watt RF** — rail daya AWR2243 di RF-EVM tidak terputus oleh deinit software.
  - Hanya `deviceMap == 1` (master) yang memanggil `rlDevicePowerOff()` asli; map lain →
    jalur `REMOVE_DEVICE_IND` (beda perilaku). Lihat `ti/mmwave/mmwave.c:1956`.
  - Memanggil `pthread_mutex_destroy(&rlAsyncEvent)` → re-power-up di proses yang sama bisa
    hang. Didesain untuk **teardown akhir sesi**, bukan power-saver runtime.
- **Konsekuensi:** untuk hemat daya idle, andalkan **relay hardware (§2.2-A)**, bukan `powerOff`.
  Namun `powerOff` tetap penting sebagai **teardown bersih tiap sesi** — lihat §5 & §7
  (referensi TI selalu memanggilnya; kode kita tidak).

### 2.2 Rekomendasi (urut dampak)

**A. (Paling besar) Hard power-cycle seluruh TIDEP via relay yang dikontrol RPi.**
- Tambah relay/MOSFET high-side (atau smart-PDU) pada input daya TIDEP, dikendalikan GPIO RPi.
- Pola tiap siklus: power-ON → tunggu boot TDA + `apps.out` siap → capture → transfer →
  **power-OFF** selama sisa periode (idle ~13–14 menit @0 W untuk radar).
- Pada duty 2.5%, ini memangkas energi idle radar+TDA mendekati nol → **penghematan terbesar**.
- **Bonus:** setiap siklus mulai dari kondisi bersih → otomatis menyelesaikan mayoritas
  masalah reliability di §5 (RF init -8 / TDA connect -1 yang butuh "restart manual").
- Konsekuensi yang harus diuji: **waktu boot TDA** (NVMe mount + Vision SDK load) +
  re-link ethernet harus muat dalam anggaran siklus. Ukur dulu; jadikan parameter
  `--warmup` di pipeline.
- Catatan musim dingin (lihat `paperA_progress_and_decisions.md` §E): mematikan radar
  menghilangkan "panas gratis" yang membantu di suhu < 0 °C — modelkan trade-off ini.

**B. (Jika A belum bisa) Power-down radar saja via mmwavelink antar capture.**
- Expose `MMWL_powerOff`/`rlDevicePowerOff` di `mmwcas.pyx` dan panggil setelah de-arm;
  power-up lagi sebelum capture berikutnya. Menghemat sebagian besar 12–14 W RF saat idle,
  tanpa mematikan TDA. Lebih ringan daripada relay tetapi penghematan board TDA tidak didapat.

**C. (Mudah, hemat board TDA — perlu hati-hati, ubah di DSP) **
> Catatan: opsi C mengubah konfigurasi DSP, **belum dilakukan**. Hanya saran.
- Matikan GUI yang sia-sia: `weston`/PowerVR pada operasi headless.
- Ganti governor ke `ondemand`/`conservative` (walau hanya 1 freq tersedia, mengurangi sedikit).
- Akar penyebab daya TDA adalah **busy-wait `apps.out`** (desain TI Vision SDK) yang sulit
  diubah tanpa source SDK — inilah alasan opsi A (matikan total) lebih efektif daripada
  menambal di dalam OS.

**D. Suspend-to-RAM TDA (`echo mem > /sys/power/state`).**
- Secara teori bisa, tapi butuh **wake source** (RTC/GPIO/Wake-on-LAN) yang terhubung ke
  RPi, dan koneksi ethernet/`apps.out` harus pulih setelah resume — kompleks dan rapuh.
  Opsi A (power-cycle bersih) lebih sederhana & lebih andal untuk deployment unattended.

## 3. Mempercepat Transfer Data (saat ini ~200 s untuk 1.29 GB, SCP)

### 3.1 Akar masalah teridentifikasi

- **Link Ethernet TDA = 100 Mbps/Full** (dmesg: `cpsw ... eth0: Link is Up - 100Mbps/Full`).
  Pada 100BASE-T, throughput maksimum teoretis ~12.5 MB/s; SCP nyata ~6.4 MB/s (sesuai laporan).
- **Namun PHY adalah TI DP83867 — gigabit-capable** (`phy ... driver TI DP83867`). RPi 5 juga
  gigabit. Artinya 100M kemungkinan akibat **kabel (CAT5 jelek / hanya 2 pasang), autonegosiasi,
  atau setting link**, bukan batas PHY. **Ini peluang terbesar.**
- **SCP via Dropbear di A15 lambat**: enkripsi membebani CPU A15 yang lemah → throughput < kapasitas link.
- Tooling tersedia di TDA: **`nc` (netcat), `tar`, `gzip`** (tidak ada rsync/lz4).

### 3.2 Rekomendasi (urut dampak)

**A. Paksa link ke 1000 Mbps.** Jika berhasil, transfer 1.29 GB bisa turun dari ~200 s
   ke ~13–25 s (10× target, dibatasi disk/CPU). Cara cek/uji:
   - Periksa kabel (wajib CAT5e/CAT6 4-pasang utuh) dan port RPi.
   - `ethtool` tidak ada di TDA (Dropbear/Arago minimal); cek dari sisi RPi:
     `ethtool <iface>` untuk lihat speed/advertised modes, dan paksa autoneg gigabit.
   - Verifikasi via dmesg TDA setelah relink: harus muncul `Link is Up - 1000Mbps/Full`.
   - **Catatan:** ada kemungkinan EVM/board ini memang dibatasi 100M secara desain — buktikan dulu.

**B. Ganti SCP → `tar | nc` (tanpa enkripsi).** Menghilangkan overhead cipher Dropbear di A15:
   - Di TDA (kirim): `tar -C /mnt/ssd -cf - <dir> | nc -l -p 5002`
   - Di RPi (terima): `nc <tda_ip> 5002 | tar -C <PostProc> -xf -`
   - Data ADC ~incompressible → **jangan** gzip (buang CPU). Untuk jaringan terpercaya
     point-to-point, kehilangan enkripsi tidak masalah (LAN privat radar).
   - Bisa beri percepatan signifikan bahkan **sebelum** link gigabit, karena saat ini CPU
     cipher kemungkinan ikut membatasi (~6.4 MB/s < ~12 MB/s kapasitas 100M).

**C. Kombinasi B + link gigabit** = hasil terbaik. Setelah itu bottleneck bergeser ke
   baca NVMe / tulis SD RPi (PostProc di SD card per komentar di `pipeline.py`).

**D. Alternatif arsitektur (future work):** turunkan **volume data sumber**. Saat ini
   1.29 GB/capture (512 ADC samples, 16 loops, full 60 m range). Untuk jembatan, max range
   efektif jauh lebih kecil — namun pengurangan harus dilakukan di firmware/konfigurasi
   capture, dan PS selection butuh SLC penuh. Catat sebagai limitasi arsitektur (sejalan
   `paperA_experiment_plan.md` Bagian 4: "SCP bottleneck = keterbatasan TIDEP, laporkan
   sebagai limitasi + future work board on-chip").

## 4. Menjalankan Edge Processing Langsung di DSP (hindari transfer)

**Kesimpulan: tidak praktis dalam waktu dekat.** Alasan konkret dari hasil eksplorasi:

| Hambatan | Detail |
|----------|--------|
| Tidak ada stack saintifik | Hanya `/usr/bin/python` = **Python 2**, **numpy tidak ada**, scipy/matplotlib tidak ada. `mimo_processing.py`/`ps_monitoring.py` bergantung penuh pada numpy/scipy. |
| CPU sudah jenuh | 2× A15 @1GHz **100% dipakai `apps.out`** (busy-wait). A15 jauh lebih lemah dari A76 RPi5. |
| RAM/Storage rootfs | rootfs 1.5 GB, **sisa hanya 406 MB** — tak cukup untuk memasang numpy/scipy/BLAS. |
| Risiko stabilitas | TDA adalah perangkat capture kritis (`apps.out`); menumpang beban berat berisiko mengganggu capture. |
| Alternatif DSP C66x | Secara teori C66x bisa FFT (DSPLIB), tapi berarti **menulis ulang seluruh pipeline PS-interferometry dalam C DSP** — effort sangat besar, di luar lingkup. |

**Rekomendasi:** pertahankan processing di RPi 5 (A76, numpy/scipy matang). Daripada
memindah compute, **hilangkan biaya transfer** lewat §3 (gigabit + `tar|nc`). Itu memberi
sebagian besar manfaat "tanpa nunggu transfer" tanpa risiko menyentuh DSP.

> Keuntungan teoretis Q4 (data sudah ada di NVMe TDA → 0 transfer) nyata, tetapi biaya
> rekayasa & risiko jauh melebihi manfaat dibanding sekadar mempercepat link.

## 5. Investigasi Capture-Failed ("not connected", "arm failed", dll.)

### 5.1 Bukti dari log `experiment-log/20260510 Outdoor/Log-Capture-RaspberryPi-20260510-1510.txt`

Statistik (3621 baris log): **13 siklus sukses vs 12 "Capture failed — retrying"** (≈48% gagal).
Rincian jenis kegagalan:

| Pesan | Status | Jumlah | Tahap |
|-------|--------|--------|-------|
| `[MMWCAS-DSP] Couldn't connect to TDA board!` | -1 | 1 | TDA init (TCP 5001) |
| `[ALL] RF init failed!` (devmap 15) | **-8** | 3 | `MMWL_rfInit` semua device |
| `[SLAVE] Error: Failed to enable master RF` (devmap 14) | **-8** | 3 | `MMWL_rfEnable` slaves |
| `[MASTER] Error: Failed to enable master RF` (devmap 1) | **-8** | 1 | `MMWL_rfEnable` master |
| `[MMWCAS-RF] Failed to stop frame!` | -2 | 2 | stop frame |
| `mimo.py exited with code 248` (= -8 & 0xFF) | — | 7 | konsekuensi -8 di `check()` `exit()` |
| `mimo.py exited with code 255` | — | 1 | (siklus di-Ctrl+C) |

**Pola dominan: status `-8` saat `rfEnable`/`rfInit`** = timeout menunggu async-event/respons
dari AWR2243 (mmwavelink). Bisa muncul di master saja, slave saja, atau semua (devmap 15).

### 5.2 Analisis akar penyebab

1. **Kegagalan `-8` adalah RF/SPI/async-event yang intermiten** (settling RF, jitter timing
   SPI, atau device dalam state tak konsisten). Outdoor (suhu/EMI/koneksi konektor RF-EVM)
   memperburuk.
2. **`check()` memanggil `exit(status)` saat `is_required=TRUE`** (di `initMaster`,
   `initSlaves`, `configure`). Saat init gagal di tengah, `mimo.py` keluar **meninggalkan
   chip AWR2243 dalam keadaan setengah-terkonfigurasi/menyala**.
3. **Retry pipeline hanya menjalankan ulang `mimo.py`** (`continue` + `time.sleep(10)`),
   yang memanggil `MMWL_DevicePowerUp` (termasuk `resetDevice()` soft-reset). Tetapi
   **soft-reset via mmwavelink sering tidak cukup membersihkan state** bila device sudah
   "ngambek" → makanya butuh **restart manual (power-cycle fisik)**.
   - **Temuan baru (vs referensi TI):** kode kita **tidak pernah memanggil `MMWL_powerOff`
     teardown** di akhir sesi, padahal sampel resmi TI (`mmw_monitoring.c :: MMWL_App`)
     **selalu** power-off semua device (slave dulu, master terakhir) sebelum disconnect.
     Karena `pipeline.py` menjalankan `mimo.py` baru tiap siklus **tanpa teardown**, chip
     masuk siklus berikutnya dari state powered yang belum dibersihkan → memperbesar
     peluang `-8`. Detail lengkap di **§7**.
   - **Timeout kecil**: macro di `ti/mmwave/mmwave.h` — `RF_INIT_TIMEOUT=1000 ms`,
     `START_TIMEOUT=1000 ms`, `INIT_TIMEOUT=2000 ms`, `TDA_TIMEOUT=3000 ms`. Inilah ambang
     yang memicu `-8` saat async-event AWR2243 telat di kondisi lapangan.
4. **`Couldn't connect to TDA` (-1)**: `apps.out`/jaringan belum siap (mis. setelah boot,
   atau `apps.out` sibuk/hang) → socket 5001 tak menerima. Konsisten dgn catatan lapangan
   "IP belum di-set / perlu `configure_ip.sh`".
5. **`Failed to stop frame` (-2)**: kemungkinan framing tak pernah benar-benar mulai /
   sudah berhenti; menghasilkan direktori kosong (sudah ada guard `idx.bin missing` di pipeline).

### 5.3 Rekomendasi perbaikan (untuk `mimo.py` / `mmwcas.pyx` / pipeline)

> Saran desain — **belum diterapkan** (sesuai permintaan jangan ubah apa pun).

1. **Hard power-cycle radar saat retry** (sinergis dgn §2-A relay). Reset fisik
   AWR2243 + TDA = pemulihan paling andal untuk `-8`. Jika relay terpasang, retry =
   power-off → tunggu → power-on → ulang init. Ini menghilangkan "restart manual".
2. **Jangan `exit()` keras di kegagalan init.** Ubah jalur konfigurasi agar
   mengembalikan status error ke Python (mode "is_required=0" untuk tahap RF), sehingga
   `mimo.py` bisa melakukan **power-down bersih + reset + retry bertahap** alih-alih keluar
   dengan code 248 dan meninggalkan device kotor. (Perlu expose `MMWL_powerOff` di Cython.)
3. **Exponential backoff + batas retry** di `pipeline.py` (saat ini fixed 10 s tanpa batas).
   Mis. 5 s → 15 s → 30 s, dan setelah N gagal beruntun → power-cycle penuh / alarm telemetri.
4. **Pre-flight check koneksi TDA** sebelum init: tes TCP ke port 5001 (atau ping + cek
   `apps.out` listen) sebelum mengirim perintah; bila gagal, tunggu/power-cycle, jangan
   langsung lanjut config.
5. **Tambah delay/verifikasi setelah power-up** (`sopTimeout`/`rlClientCbsTimeout` saat ini
   1000 ms). Pada kondisi lapangan, menaikkan margin atau memverifikasi async-event sukses
   sebelum lanjut bisa mengurangi `-8`.
6. **Telemetri kesehatan** (sejalan paperA §E watchdog): hitung & kirim jumlah fault per
   jenis + auto-recovery (untuk klaim C4 "self-recovering" yang butuh kuantifikasi).

## 6. Timestamp Milidetik untuk "Arming TDA" & "Framing"

### 6.1 Kondisi sekarang

- Pesan `[MMWCAS-DSP] Arming TDA` dan `[MMWCAS-RF] Framing ...` dicetak dari fungsi Cython
  **`check()`** (di `mmwcas.pyx`) memakai `printf` **tanpa timestamp**, **setelah** API
  terkait (`MMWL_ArmingTDA`, `MMWL_StartFrame`) kembali.
- Urutan di `mimo.py`: `mmw_arming_tda()` → `time.sleep(2)` → `mmw_start_frame()` →
  `time.sleep(duration)` → `mmw_stop_frame()` → `mmw_dearming_tda()`.
- **Framing (capture sesungguhnya) dimulai di `mmw_start_frame()`**, yang memanggil
  `MMWL_StartFrame(1<<i)` untuk i = 3→0. **Master (i=0) di-trigger TERAKHIR** → titik nol
  capture paling tepat adalah tepat setelah StartFrame master kembali.

### 6.2 Rekomendasi (cara termudah, presisi ms, tanpa rebuild Cython)

> Saran kode — **belum diterapkan**. Cukup ubah `mimo.py` (sisi Python), tidak perlu
> menyentuh DSP atau mem-build ulang `mmwcas`.

Tambahkan timestamp ms-precision tepat mengelilingi pemanggilan, mis.:

```python
def _now_ms():
    return datetime.now().strftime("%Y-%m-%d %H:%M:%S.%f")[:-3]  # milidetik

# ... sekitar arming:
print(f"[TS] ARM_TDA_begin  {_now_ms()}")
status = mmwcas.mmw_arming_tda(capture_dir)
print(f"[TS] ARM_TDA_end    {_now_ms()}  status={status}")

time.sleep(2)

print(f"[TS] FRAMING_begin  {_now_ms()}")
status = mmwcas.mmw_start_frame()
print(f"[TS] FRAMING_end    {_now_ms()}  status={status}  <-- t0 capture (master triggered last)")
```

- `FRAMING_end` ≈ **t0 capture sebenarnya** (master di-trigger terakhir di `mmw_start_frame`).
- Untuk presisi lebih tinggi/monotonic, gunakan `time.perf_counter_ns()` paralel dengan
  wall-clock untuk durasi antar event.
- **Sinkronisasi ground-truth (accelerometer):** ini langsung mendukung kebutuhan di
  `paperA_experiment_plan.md` Bagian 3 ("timestamp/trigger bersama radar↔accel WAJIB sinkron
  dari awal"). Pastikan RPi ber-NTP-sync; catat offset NTP. Idealnya, untuk validasi modal,
  picu trigger bersama atau samakan basis waktu radar & accel sejak awal.

### 6.3 Jika butuh timestamp di dalam driver (opsional, perlu rebuild)

- Modifikasi `check()` di `mmwcas.pyx` agar mencetak waktu (mis. `clock_gettime`) bersama
  pesan, lalu `make build`. Lebih invasif; opsi §6.2 sudah cukup untuk kebutuhan sinkronisasi.

## 7. Perbandingan Urutan API: kode kita vs referensi resmi TI (DFP Bab 9)

Sumber otoritatif urutan = sampel resmi TI **`mmWaveLink_Cascade_Monitoring/mmw_monitoring.c`**
fungsi **`MMWL_App()`** (basis `mimo.c`). DFP Bab 9 ("AWR2243 Two/Four chip API sequence")
menampilkannya sebagai gambar (Figure 15–16), tapi `MMWL_App()` adalah implementasinya.

> Catatan: untuk cascade, DFP menyebut set `RL_CASCADE_NUM_DEVICES` = 4 di `mmWaveLink.h`
> agar SPI paralel ke semua chip.

| Tahap | Referensi TI (`MMWL_App`) | `mimo.c` | `mimo.py` (via `mmwcas`) | Status |
|---|---|---|---|---|
| Connect TDA | `TDAInit` | `MMWL_TDAInit` (configure) | `mmw_init`→`TDAInit` | ✅ sama |
| Power-up master | `DevicePowerUp(master)` + `DeviceInit1` | `initMaster` | dalam `mmw_init` | ✅ sama |
| Power-up slaves | loop `DevicePowerUp(slave)` + `DeviceInit1` | `initSlaves` | dalam `mmw_init` | ✅ sama |
| Config semua | `DeviceInit2` + `DeviceConfig` | `configure(...)` | dalam `mmw_init` | ✅ sama (grouping beda) |
| Frame config | `FrameConfigAll` | frame master + slaves | dalam `mmw_init` | ✅ sama |
| Arm TDA (capture) | (jalur capture-card) | `ArmingTDA` | `mmw_arming_tda` | ✅ ada di kita (capture) |
| **Start frame** | **slaves (2→0), master TERAKHIR** | `for i=3→0 StartFrame` (master last) | `range(3,-1,-1)` | ✅ **urutan benar** |
| Stop/tunggu | tunggu async frame-end + `osiSleep(framePeriodicity)` | `msleep(duration)` lalu `StopFrame` | `sleep(duration)`, `stop_frame` | 🟡 kita pakai sleep tetap (OK untuk numFrames=0) |
| **Power-OFF teardown** | **`powerOff` slaves (2→0), master TERAKHIR** | **TIDAK ADA** | **TIDAK ADA** | ❌ **selisih utama** |
| Disconnect | `ethernetDisconnect` | `DeArmingTDA` | `mmw_dearming_tda` | 🟡 mirip (de-arm, bukan power-off) |

### Temuan kunci dari perbandingan

1. **Urutan start-frame kita SUDAH benar** — slave dulu, master terakhir (sesuai TI).
   Master di-trigger terakhir = titik t0 capture sebenarnya (relevan untuk §6 timestamp).
2. **Kita melewatkan `MMWL_powerOff` teardown** yang TI lakukan di SETIAP akhir sesi
   (urutan: slave 2→0 lalu master). Ini perbedaan paling material:
   - Untuk **reliability (#5)**: tiap siklus `mimo.py` baru memulai dari chip yang belum
     di-teardown → kontributor `-8`. Menambah `powerOff` di akhir `mimo.py` (mirror TI)
     membuat tiap siklus mulai bersih. Aman karena proses tetap keluar setelah itu
     (mutex async memang untuk teardown).
   - Untuk **power (#2)**: ini teardown software (bukan pemutus daya RF) — tetap tidak
     menggantikan relay, tapi melengkapi siklus sesuai desain TI.
3. **De-arm vs power-off**: kita memanggil `DeArmingTDA` (lepas arming capture) tapi tidak
   `powerOff` device. Referensi melakukan keduanya secara konseptual (capture stop + powerOff
   + ethernetDisconnect). Menyelaraskan ini = lebih dekat ke alur resmi TI.
4. **Implikasi rekomendasi (belum diterapkan):** expose `MMWL_powerOff` + `MMWL_DeviceDeInit`
   di `mmwcas.pyx`, lalu panggil power-off (slave→master) sebelum `mimo.py` keluar. Bila
   relay (§2.2-A) dipasang, urutan ideal: software teardown → de-arm → **relay OFF**.

### 7.1 Verifikasi terhadap Figure 14–16 DFP (dikirim user)

Figure resmi DFP (14 single-chip, 15–16 cascade) mengkonfirmasi detail kode kita **sudah benar**:

| Detail figure | Kode kita | Status |
|---|---|---|
| Channel config cascading per device: master `[Cascading=0x1]`, slave `[0x2]` (Fig 15) | `initMaster` casc=1, `initSlaves` casc=2 | ✅ |
| Frame trigger: master `[Trigger=0x1]` SW, slave `[0x2]` HW (Fig 16) | `MMWL_frameConfig`: `deviceMap==1→triggerSelect=1` else `2` (`mmwave.c:1497`) | ✅ |
| Master penuh dulu (PowerOn→FW→RfPowerUp→ChannelCfg), baru slave (Fig 15) | `initMaster` lalu `initSlaves` | ✅ |
| `rlSensorStart/Stop` = framing (Fig 16) | `StartFrame`→`sensorStart`, `StopFrame`→`sensorStop` | ✅ |

Error `-8` memetakan persis ke 3 titik tunggu async-event di figure:
`RL_MSS_POWERUP_COMPLETE`, `RL_RF_POWERUP_COMPLETE`, `RL_RF_AE_INITCALIBSTATUS_SB`.

### 7.2 🔴 Temuan arsitektural: re-init penuh tiap siklus (akar #5 + bottleneck init)

Figure menunjukkan struktur 2-fase: **fase berat SEKALI** (FileDownload firmware → RfPowerUp →
`rlRfInit` kalibrasi) lalu **fase ringan BERULANG** (`sensorStart`/`sensorStop`).

- **`mimo.py` SUDAH mengikuti pola TI**: `mmw_init()` dipanggil **sekali** (baris 94), loop hanya
  `arming→start_frame→stop_frame→dearm` (tanpa re-init).
- **TAPI `pipeline.py` memanggil `mimo.py --num-loops 1` tiap siklus** → proses baru tiap siklus →
  **fase berat diulang SETIAP siklus** (download firmware ke 4 chip + RF power-up + kalibrasi).
- Akibat: (a) **3× peluang `-8` per siklus** (vs 1× di pola TI), (b) **~85–95s overhead init/siklus**
  yang sebenarnya tak perlu diulang.

**Dua arsitektur koheren:**

| | A. Persistent session | B. Power-cycle tiap siklus |
|---|---|---|
| Pola | init **sekali**, loop `arm→start→stop→dearm` (mimo.py dukung via `--num-loops 0`) | relay OFF saat idle; cold-boot + init penuh tiap siklus |
| `-8` | jauh berkurang | init penuh tiap siklus, tapi cold-start bersih |
| Kecepatan | hilangkan ~85–95s/siklus | tetap bayar init penuh |
| Hemat daya | radar tetap nyala (+`rlRfDynamicPowerSave`/relay) | maksimal |

**Rekomendasi:** karena `paperA_progress` menunjukkan **energy autonomy 4.6×** (daya bukan kendala
mengikat), **Arsitektur A** lebih unggul — refactor `pipeline.py` agar capture didorong lewat **satu
sesi mimo persisten** (init sekali). Menyelesaikan reliability `-8` **dan** memangkas waktu siklus.
Relay (B) tetap berguna sebagai mekanisme recovery saat benar-benar hang.

### 9.2 🎯 Workflow lab = Arsitektur A (validasi `pipeline-persistent.py`)

Script terbagi **dua file terpisah**:
- `BridgeSpan.lua` = **KONFIGURASI** (connect → SOP → firmware → RF → config → RfInit) — **SEKALI**.
- `Cascade_Capture_Loop.lua` = **CAPTURE LOOP** (`while`: arm → start frame → wait → transfer) — **berulang tanpa re-config**.

`pipeline.py` (re-init tiap siklus) menyimpang dari workflow standar TI.

### 9.3 Finite framing vs infinite+stop (akar error `-2`)

Lua memakai **`nframes_master = 1000` (finite)** dengan `framing_type=1` → device **auto-stop**
setelah 1000 frame, dan blok StopFrame **dilewati**:
```lua
if (framing_type == 0) then   -- StopFrame manual HANYA jika infinite
    Framing_Control(...,0)
end
```
Kode kita pakai **`numFrames=0` (infinite) + `time.sleep` + StopFrame manual** — dan di sinilah
error **"Failed to stop frame `-2`"** muncul di log 20260510. Lihat **§9.6** untuk kenapa finite
framing pernah error di kode kita & cara benar mengimplementasikannya.

Manfaat finite framing: hilangkan StopFrame `-2`, **jumlah frame deterministik** (1000 persis,
bukan variabel) → membantu konsistensi resolusi frekuensi (`paperA`: σ/μ 56%).

### 9.4 Transfer & ukuran data

- `TransferFilesUsingWinSCP_mult(1)` → rekan lab **juga pakai SCP (WinSCP)**. SCP = baseline TI;
  `tar|nc` (§3.2) adalah peningkatan, bukan penyimpangan.
- **`data_packaging`** (0=16-bit, 1=**12-bit packed**) → buang 4 LSB → **data −25%** (1.29 GB →
  ~0.97 GB), transfer lebih cepat. Trade-off: `mimo_processing.py` harus unpack (`*ubit12`).
- **`n_files_allocation`** → pre-alokasi file di SSD, cegah frame-drop saat ganti file (cap 2 GB/file).
  Belum kritis (~322 MB/chip < 2 GB), relevan untuk capture panjang.

### 9.5 Detail kecil

- **SOP4 reset eksplisit** tiap config (`SOPControl_mult(...,4)`) — di kode kita ter-handle di `MMWL_DevicePowerUp`.
- **`RfInitCalibConfig_mult(...,65537)`** (mask 0x10001) — set kalibrasi boot eksplisit sebelum RfInit;
  kode kita mengandalkan default `MMWL_rfInit`. Titik tuning bila `-8` kalibrasi membandel.
- Arm→framing delay: Lua `RSTD.Sleep(1000)` (1s); kita 2s. Sepele.

### 9.6 ⚠️ Kenapa finite framing pernah error di kode kita (dugaan + cara benar)

Penyebab paling mungkin (perlu konfirmasi dgn pesan error aslinya):

1. **StopFrame pada device yang sudah auto-stop → `-2`.** Saat `numFrames=N`, radar berhenti
   sendiri setelah N frame. Tapi `mimo.py` **selalu** memanggil `mmw_stop_frame()` lalu
   memperlakukan status ≠ 0 sebagai gagal → `continue` ("capture likely failed") **padahal datanya
   ada**. Lua menghindari ini dengan **melewati StopFrame saat finite**.
2. **Timing dearm.** Setelah N frame selesai, file masih perlu di-finalize. `mmw_dearming_tda()`
   yang mem-finalize rekaman TDA — pastikan menunggu **N × framePeriodicity + margin** sebelum dearm.
3. **TDA arm `numberOfFramesToCapture=0`** (hardcoded di `mmw_arming_tda`) — sama seperti Lua
   (`num_frames_to_capture=0`), jadi ini **bukan** masalah; radar yang mengontrol jumlah frame.

**Cara benar (mirror Lua `framing_type=1`):**
- Set `numFrames = round(duration / framePeriodicity)` (mis. 30s/30ms = 1000).
- Setelah start, **tunggu** N × framePeriodicity + margin.
- **JANGAN panggil StopFrame** (atau toleransi statusnya) — langsung `dearm`.
- (Belum diimplementasikan — menunggu konfirmasi pesan error asli user.)
